# Live FIRST rehearsal tool

`first-rehearsal.py` builds and runs one SSH session that performs the FIRST live rehearsal: identity gate, prerequisite check, snapshot, empty install, verify, exact uninstall, restoration proof and connectivity check. `first-rehearsal.sh` is the remote POSIX/BusyBox ash script; the Python tool embeds the committed `router/` tree and the configuration values into it. Read the [runbook](../../docs/runbooks/live-first-rehearsal.md) before use.

The tool uses only the Python standard library and refuses to run unless started with `python3 -I`.

## Configuration schema

Keep the real configuration outside the repository, in a private directory. [`config.example.json`](config.example.json) uses fictional MACs (`02:00:00:00:00:xx`) and documentation IPs (`192.0.2.0/24`). The tool validates strictly: it rejects unknown keys, missing keys, duplicate keys and non-canonical values.

| Key | Type | Rule |
|---|---|---|
| `schemaVersion` | integer | Exactly `1` |
| `host` | string | Router LAN IPv4 in canonical dotted form; the tool always connects as `root@<host>` |
| `adminPublicKeyPath` | string | Absolute, normalized path to the admin **public** key. Its fingerprint must equal `adminKeyFingerprint`. The private key stays in the agent; the tool never reads it |
| `adminKeyFingerprint` | string | `SHA256:` followed by 43 base64 characters, as printed by `ssh-add -l` |
| `knownHostsPath` | string | Absolute path to a regular file holding the pinned router host key (`StrictHostKeyChecking=yes`) |
| `evidenceDir` | string | Absolute path to an existing directory you own, with no group or other write access. It is refused under `/tmp`, `/run`, `/dev/shm`, `/var/tmp` or on tmpfs. Each run creates a new `<UTC>-first-rehearsal/` directory there |
| `authorizationPath` | string | Absolute path to a regular file recording the user's approval of this exact run. Its sha256 goes into the evidence |
| `deadlineUtc` | string | `YYYY-MM-DDTHH:MM:SSZ`. `execute` refuses unless now + local timeout + 300 s is no later than this time |
| `platformProfile` | string | Optional. One of `strict`, `gl-xe3000-4.8.3-logd-011-v1`, `gl-xe3000-4.8.3-os-trust-v1` (the default) |
| `remoteTimeoutSeconds` | integer | Optional, 600–3600, default 1800. Generous last-resort router-side `timeout -s KILL`; the script bounds itself first. The local timeout is this value + 60 s |
| `roles.management` | object | `{"ip", "mac"}`. The SSH client device. Its MAC is protected |
| `roles.jd_adult` | object | `{"ip", "mac"}`. The adult device that must stay connected. Its MAC is protected |
| `roles.penn_child` | object | `{"ip", "mac"}`. The child device. It must be present, but it is **not** enrolled |
| `protectedHistoricalMacs` | array | 1–32 MACs to protect (for example Bryn's) that need not be present. None may equal a live role MAC |

MACs must be canonical lowercase `aa:bb:cc:dd:ee:ff`, unicast and non-zero. Live role MACs and IPs must be distinct from each other and role IPs from `host`, with one exception: `management` and `jd_adult` may have exactly the same IP **and** MAC (for example, both `192.0.2.10` / `02:00:00:00:00:10`). Matching only one field is refused. Child roles must remain distinct, and historical MACs must remain unique and separate from every live role. Repeated adult `--protect` arguments are deduplicated by the installer. Evidence explicitly labels the adult and management probes as sharing one confirmed device; this does not establish connectivity for a second adult device.

## Release identity and the shipped tree

The payload ships only the emitted tree: the entries of `router/release.sha256` plus `release.sha256` itself (the bytes `tools/freeze-router-release.py --emit` writes; wrappers stripped of `CF_TEST_MODE` blocks, modes 644/755/600). `router/cron` and `router/firewall.include` are tracked but not in the manifest and not used by `install.sh`, so they are never shipped. Any other tracked `router/` file outside the manifest, and any manifest entry whose file is missing, duplicated or malformed, refuses the plan (two-way check). The manifest must also list exactly the router's fixed set of 15 files (`install.sh`, `uninstall.sh`, `cfctl`, `cfctl-ssh`, `cfctl-scope`, `lib/platform-bootstrap.sh` and the nine `lib/` modules), the set `platform-bootstrap.sh` accepts; any other entry set refuses. The stripped `cfctl-ssh` and `cfctl-scope` must pass `sh -n`, as in the freezer.

Before anything is built the tool recomputes `CF_RELEASE_ID` from the shipped bytes with the freezer's formula and refuses on any mismatch: the nine module hashes, `cfctl` with its pin line blanked, and the stripped `cfctl-ssh` and `cfctl-scope`. It also requires `CF_RELEASE_MODULES` to equal the shipped module hashes, and `CF_BOOTSTRAP_PIN` in `install.sh`, `uninstall.sh` and `cfctl` to equal the hash of the shipped `platform-bootstrap.sh`.

`plan` discloses `emittedTreeSha256` (sha256 over the sorted lines `mode path sha256` of the emitted tree), and it is part of the plan digest, so the approval binds the emitted bytes and not only a commit. A test compares the tree and the id with `freeze-router-release.py --emit` output. The VERIFY phase then checks, on the router, each file listed in the manifest in the release directory named by the id and, for `cfctl*` and `lib/*`, in the place the installer puts it under `usr/sbin` and `usr/lib/couvrefeu`. Each must be a regular file and not a symlink (a FIFO or other special file is refused without being read), and its sha256 must equal the shipped digest; the installed `CF_RELEASE_ID` is checked too. Only those listed files are claimed to hash-match: modes, owners, extra files and the symlink status of parent directories are not compared.

If a listed file in the release directory or under `usr/lib/couvrefeu` (the inputs of the installed `uninstall.sh`) fails that check, the script does **not** run the installed `uninstall.sh` as root. It stops at VERIFY with `PHASE VERIFY FAIL installed_uninstall_inputs_mismatch <paths>; uninstall not attempted; journal retained` and `FAIL_AFTER_MUTATION VERIFY`, leaving Couvre-feu installed with its journal (`/etc/couvrefeu/backup`). Recovery is then a manual password login, which this tool never disables; resolve the cause by hand, and do not delete the journal. A mismatch only under `usr/sbin` is reported as `PHASE VERIFY FAIL installed_tree_mismatch` and the run continues to the normal uninstall, which fails the final result.

## Penn pilot, one or two devices (`penn-pilot.py`)

`penn-pilot.py` performs gate 3 of the [ordered live gates](../../docs/integration-004.md#ordered-live-gates) in one SSH session. It uses the same configuration schema. Use a separate config copy whose `authorizationPath` records approval of this exact pilot. Each run creates a `<UTC>-penn-pilot/` evidence directory. Here, `penn_child` **is** enrolled, and its MAC (with `penn_child_2`, both MACs) is the only MAC the policy may contain. The tool asserts this locally and again on the router before any write. With two devices the router does not trust the device-set parameters: in PAYLOAD it recomputes the `LC_ALL=C`-sorted pair from the two MACs that IDENTITY checks and refuses (`device_set_mismatch`) unless the `--rpc-allow` list and the expected `observed.kids` equal it. `remoteTimeoutSeconds` must cover the disclosed worst case (`minimumRemoteTimeoutSeconds` in the plan); with the default timing that is 3,318 s, so raise it from the 1,800 s default. The minimum is the pre-mutation budget (360 s) + one safe-band wait and the install allowance (72 + 240 s) + the per-phase worst cases (ENROLL 609, PAUSE 465, RESUME 345, EXPIRY 847, DNS 80 s; each `cfctl` call is a 72 s safe-band wait + 45 s, each counters snapshot 80 s, each probe iteration 40 s, each status settle 178 s) + the 300 s teardown reserve. A status settle is the first attempt's neighbor read (8 s) + the `timing.statusSettleSeconds` window (45 s) + one attempt admitted at least 1 s before the window closes (one 117 s `cfctl` call + 8 s neighbor read; the spare second absorbs 1 s clock granularity and the neighbor-hash forks); ENROLL and EXPIRY each carry one. Two devices add one `cfctl rpc-activity` call to ENROLL (726 s), so the minimum becomes **3,435 s**; the SCOPE phase adds one `cfctl` call plus two firewall-state reads (3 × 8 s each), 165 s, giving **3,483 s** for one device with SCOPE and **3,600 s** for two devices with SCOPE. Every shape now exceeds a 3,300 s config, so raise `remoteTimeoutSeconds` to at least the plan's minimum (the cap is 3,600 s, which two devices with SCOPE need exactly); the plan refuses below it. On the router, each phase starts only if elapsed time plus its worst case still leaves the teardown reserve, and every observe/expiry iteration and counters snapshot re-checks this; otherwise the pilot stops into teardown (`remote_budget_reserved_for_teardown`). Every timed pause is extended by the slowest `cfctl` call measured so far in the session (capped at the 45 s `cfctl` allowance, which the EXPIRY worst case adds on top of the pause length; the plan's `timing.cfctlAllowanceSeconds` discloses it), so a pause cannot lapse inside its own `cfctl pause` on a loaded host; the call still runs exactly once. Read-only `iptables`/`ipset` reads run under `timeout -s KILL 8`. `cfctl` calls are not KILL-wrapped: a killed `cfctl` could leave its runtime or platform lock behind and make the single uninstall refuse.

```sh
python3 -I tools/live/penn-pilot.py plan CONFIG      # disclose, then:
python3 -I tools/live/penn-pilot.py execute CONFIG --expect-plan-sha256 HEX
```

### Optional private-config keys

Both are read only by `penn-pilot.py` (the rehearsal schema is unchanged) and live only in the private config. Without them the payload parameters, policy, phases, timing and minimum are exactly those of the single-device pilot.

| Key | Rule |
|---|---|
| `roles.penn_child_2` | `{ip, mac}` of a second device of the same person `penn`. Canonical unicast MAC; its MAC and IP must differ from every role, the host, every protected historical MAC and the scope test MAC. The install uses `--rpc-allow` once per device in sorted order, the policy names person `penn` with both MACs (sorted), and the plan discloses both MACs (from this private config only) |
| `scopeNegativeTest` | `true` or `false` (default). `true` adds the SCOPE phase between ENROLL and PAUSE |

The remote script is the filled `first-rehearsal.sh` with its final call removed, followed by `penn-pilot.sh`, which reuses every `cfr_*` helper. It runs these phases in order:

| Phase | What happens |
|---|---|
| PAYLOAD, IDENTITY, PREREQ, SNAPSHOT | As in the rehearsal. In addition, Penn must be REACHABLE/DELAY, own exactly one IPv4 neighbor row and one lease, and no protected MAC may appear on Penn's IP. With two devices the second device passes the same checks (`penn_child_2_*` reasons), and neither Penn MAC may appear on the other's IP. PREREQ validates the exact `--rpc-allow` arguments |
| BASELINE | Router-side DNS (`nslookup example.com <router LAN IP>`, centisecond timing), management/JD ping and crond count (split: `etc` = crond whose crontab dir resolves to `/etc/crontabs`, `other` = any other crond such as GL firmware's `-c /tmp/gl_crontabs`; the `MEASURE crond_processes` line reports `baseline=etcN,otherM`). All read-only. Tolerance: baseline maximum + 1.5 s DNS, + 500 ms management RTT. A ping is a STOP signal only if it answered at baseline |
| INSTALL | Scoped activation `--rpc-allow <penn MAC> [--rpc-allow <second MAC>] --activate`. No `authorized_keys` or service-key provisioning (`service_key_confinement: unmeasured, not exercised`) |
| ENROLL | `cfctl rpc-sync` with a stdin request file for a fresh generation at revision 0, sent once and never retried. Status must show only Penn's devices observed (`observed.kids` equals the sorted set). The status read is settled (see below). With two devices, one read-only `cfctl rpc-activity --json` follows: `rpc_activity_devices` is `measured listed=k/2` when the router exposes devices, `unmeasured` otherwise; a listed MAC outside Penn's set stops the pilot |
| SCOPE (optional) | Only with `scopeNegativeTest: true`. One separate `rpc-sync` (operation `penn-pilot-scope-1`, expected revision 1, the enrolled digest) whose revision-2 policy adds the synthetic MAC `02:00:00:00:00:99` to Penn. It must be cleanly rejected: non-zero exit, one reply line, errors exactly `["rpc_scope_overlap"]`, `receipt` null, accepted revision 1 with the enrolled digest and operation, observed kids unchanged, and the same fingerprint before and after. The fingerprint compares exactly three things: the `firewall.owned` slot instance (letter, inode, nanosecond mtime), every `ipset save` `create`/`add` line of a `cf*` set, and every `iptables -t filter -S` and `ip6tables -t filter -S` line with a word starting `cf` (Couvre-feu chains and sets); the `nat` and `mangle` tables are not compared (MEASURE detail `filter_ipset_slot_unchanged`). Anything else stops the pilot into teardown (`scope_not_cleanly_rejected` or `firewall_changed`); if the safe band never opens the call is not made and the stop reason is `safe_band_unavailable`. The call is never retried. IDENTITY refuses (`scope_mac_present`) if `02:00:00:00:00:99` appears in the live neighbor table or DHCP leases |
| PAUSE | Timed pause (180 s); with two devices both MACs must be in `observed.paused` and the kernel paused set (a partial set stops the pilot). REJECT counters for Penn's MAC/IP rules, read with `-S`/`-nvxL` and never `-Z`, are sampled over 60 s while adult probes run. An increase means "router-side block observed"; otherwise "packet blocking unmeasured". The paused-set REJECT rule matches the set, not a device, so with two devices the delta is an aggregate (`devices=2 aggregate_set_match_counters per_device_unavailable`) |
| RESUME | Status clean, kernel set clear, and REJECT counters must not increase |
| EXPIRY | Second timed pause (120 s) with no further `cfctl` call. The kernel set is polled read-only until cron `cfctl expire` clears it, within 150 s after `until`. The read-only status after expiry must be clean, settled as at ENROLL. crond counts are recorded with the same `etcN,otherM` split; `duplicate_etc_crond` is appended to the MEASURE line (informational, no pass/fail effect) if more than one `/etc/crontabs` crond is seen after install or during expiry |
| DNS | Router-side hit counters for the DoT/DoQ/DoH/:53 rules generated for enrolled kids (they apply while enrolled, independent of pause), plus adult router DNS timing. Every changing apply builds a new `cf2_a`/`cf2_b` slot with fresh counters, so each counters snapshot records the slot and the identity (inode, nanosecond mtime) of `firewall.owned`. Hits are summed only over windows whose two snapshots share one slot instance (enrolled→prepause, pause0→pause1, resume0→resume1, expired→final; `windows=k/4`); apply transitions and the expiry wait are not counted. A slot change or a falling counter makes a window, or packet blocking, unmeasured. No DoH list is configured, so DoH stays unmeasured. Client-side redirect/DoH is always unmeasured |
| UNINSTALL, RESTORE, CONNECTIVITY | The single teardown, as in the rehearsal |

**Status settle (ENROLL and after expiry).** `cfctl status` reports `drift:true` whenever the effective digest (usable canonical LAN address bindings plus the protected list) differs from the one recorded at the last confirm. A binding change after the confirm (a usable address appearing, disappearing or changing owner) can do this with `errors:[]` until cron `cfctl expire` re-confirms within a minute. IPv6 REACHABLE/PERMANENT/STALE/DELAY/PROBE now supply identical binding evidence, so state-only aging among them does not change the digest; FAILED/INCOMPLETE/NOARP/NONE supply none. IPv4 lease/freshness behavior remains unchanged. A prior live pilot stopped at ENROLL (`penn_not_observed`) on IPv6 reachability aging under the earlier fresh-neighbor classifier. These two gates therefore re-read status, read-only, every `pollSeconds` (with the budget check and adult probes) until the gate passes, giving up `statusSettleSeconds` (45 s, plan-disclosed and digest-bound) after the first read. Only a single-line reply with `drift:true`, `errors:[]`, `desiredRevision` and `confirmedRevision` both equal to the revision the pilot's own calls set (1 after ENROLL; +1 for each pause and the resume, so 4 after expiry, which cron `cfctl expire` does not change) and the gate's expected kids/pauses is waited out. Every clean reply must also have both revisions equal to the expected pilot revision, including the initial read and any read after drift. Non-empty errors, a null, stale or unexpected revision (including a never-confirmed apply that cron could later repair) or a kids/pauses mismatch stop immediately with the gate's reason. No `rpc-sync` or other mutating call is ever retried. Each attempt's status read is followed by `INFO status_settle_neigh <phase> attempt=N` (the read-only `ip neigh show dev br-lan` table, with IPv4 addresses kept, role MACs named, other MACs and every IPv6 address replaced by a 12-hex prefix of sha256 over a per-run salt plus the token; the salt comes from `/dev/urandom` once per run and is never logged or written, and without it the line says `salt_unavailable` and nothing is hashed) so the changed neighbor can be named within one run but not linked across runs, and the gate logs `INFO status_settle <phase> attempts=N waited_s=S` (`not_transient` or `gave_up` on a stop). A gate that passes only after re-reads also prints `MEASURE status_settle measured settled_after_drift phase=<phase> attempts=N waited_s=S`. The PAUSE, RESUME and expiry-pause gates are not settled: they check the reply line that the mutating call prints right after its own confirm, which is the evidence for that call, and a wait there would eat into the timed pause.

**IDENTITY refresh probe.** A device idle on Wi-Fi can hold a STALE neighbor entry. Before the freshness check, IDENTITY sends each Penn device two ICMP echoes from the router (`timeout -s KILL 5 ping -c 2 -W 1 -q`, the BusyBox flags `cfp_ping` already uses), with a neighbor-table read before and after the probes. If a device was initially outside REACHABLE/DELAY, its probe must succeed: transmitting alone can change STALE to DELAY without a reply. Initially fresh devices retain the existing freshness check even if ICMP is unavailable. This is a network probe, not a state change: nothing on the router is written. A device that is still not REACHABLE/DELAY is refused as before (`penn_child_not_fresh`, `penn_child_2_not_fresh`).

After `MUTATION_BEGIN`, every outcome ends in that one teardown. This includes an adult-probe STOP, a failed gate, an exhausted time budget and an installer failure, provided the installed recovery `uninstall.sh` exists. The teardown is part of the approved procedure, not a retry. If it ends with exact restoration, the last line is `PENN_PILOT_STOPPED_RESTORED`, or `PENN_PILOT_STOPPED_RESTORED_CONNECTIVITY_FAILED` (outcome `STOPPED_CONNECTIVITY_FAILED`) when the management or JD neighbor check failed afterwards; if the teardown itself fails, it is `FAIL_AFTER_MUTATION`. Only `PENN_PILOT_PASS` means that every phase passed and the snapshot matched exactly. Even then, packet blocking is claimed only when counters rose.

### If the single uninstall is absent or refuses

The last lines are then `PHASE UNINSTALL FAIL ...`, `PENN_KERNEL_STATE paused|clear|unknown` and `FAIL_AFTER_MUTATION UNINSTALL`, with `DIFF` lines showing what is left. Couvre-feu stays installed with its journal; do not retry and do not rerun install or uninstall to "clean up".

- `PENN_KERNEL_STATE paused` means Penn's MAC is still in the pause set and Penn is still blocked. The pause rules have no kernel time bound. Only `cfctl expire` (cron) or `cfctl resume penn` (a mutation that needs its own approval) lifts the pause. Both refuse while uninstall recovery markers exist under `/etc/couvrefeu/backup` (`uninstall_recovery_in_progress`), which happens when uninstall refused after kernel cleanup began. `unknown` means the set could not be read; treat it as paused.
- Do not run `cfctl remove-fw` by hand. Once recovery markers exist, it is refused without the installer's token, and only `uninstall.sh` runs it.
- Follow the [rehearsal runbook](../../docs/runbooks/live-first-rehearsal.md) failure guidance: wait for `/tmp/couvrefeu-install.lock` and `/tmp/couvrefeu-platform.lock` to clear, read `<stage>/phase.log` and `child.log` for the refusal reason (drift, lock contention, kernel cleanup), and resolve that cause explicitly. Then, as a separately approved step, run the installed `/etc/.couvrefeu-release-<id>/uninstall.sh` once. It takes no arguments, and it is the only supported way to remove the firewall slots, cron entry and files and to restore the originals. Never delete the journal (`/etc/couvrefeu/backup`).

Every `cfctl` call waits until the router clock is between seconds 15 and 45 of the minute and no runtime or platform lock is held. That way it never races the per-minute cron `cfctl expire`, which fails on lock contention instead of waiting.

The pause rules (`--match-set cf2_<slot>_p src -j REJECT` and `-o br-lan -d <ip> -j REJECT`) have **no** kernel `-m time --datestop` bound. Only cron `cfctl expire` ends a timed pause. For that reason the pilot uses only timed pauses.

On the host, a thread samples RTT and a direct DNS query to the router before, during and after the session. These samples are evidence only: they cannot stop the remote script, but a disruption beyond tolerance prevents PASS. `summary.json` labels each measurement `measured` or `unmeasured`.

Never commit real MACs or IPs. Protected devices are listed only in the private config (`protectedHistoricalMacs`).
