# Live FIRST rehearsal tool

`first-rehearsal.py` builds and runs one SSH session that performs the FIRST live rehearsal: identity gate, prerequisite check, snapshot, empty install, verify, exact uninstall, restoration proof and connectivity check. `first-rehearsal.sh` is the remote POSIX/BusyBox ash script; the Python tool embeds the committed `router/` tree and the configuration values into it. Read the [runbook](../../docs/runbooks/live-first-rehearsal.md) before use.

The tool uses only the Python standard library and refuses to run unless started with `python3 -I`.

## Configuration schema

Keep the real configuration outside the repository, in a private directory. [`config.example.json`](config.example.json) uses fictional MACs (`02:00:00:00:00:xx`) and documentation IPs (`192.0.2.0/24`). The tool validates strictly: it rejects unknown keys, missing keys, duplicate keys and non-canonical values.

| Key | Type | Rule |
|---|---|---|
| `schemaVersion` | integer | Exactly `1` |
| `host` | string | Router LAN IPv4 in canonical dotted form; the tool always connects as `root@<host>` |
| `adminPublicKeyPath` | string | Absolute, normalized path to the admin **public** key. Its fingerprint must equal `adminKeyFingerprint`. The private key stays in the agent; the tool never reads it |
| `adminKeyFingerprint` | string | `SHA256:` followed by 43 base64 characters, as printed by `ssh-add -l` |
| `knownHostsPath` | string | Absolute path to a regular file holding the pinned router host key (`StrictHostKeyChecking=yes`) |
| `evidenceDir` | string | Absolute path to an existing directory you own, with no group or other write access. It is refused under `/tmp`, `/run`, `/dev/shm`, `/var/tmp` or on tmpfs. Each run creates a new `<UTC>-first-rehearsal/` directory there |
| `authorizationPath` | string | Absolute path to a regular file recording the user's approval of this exact run. Its sha256 goes into the evidence |
| `deadlineUtc` | string | `YYYY-MM-DDTHH:MM:SSZ`. `execute` refuses unless now + local timeout + 300 s is no later than this time |
| `platformProfile` | string | Optional. One of `strict`, `gl-xe3000-4.8.3-logd-011-v1`, `gl-xe3000-4.8.3-os-trust-v1` (the default) |
| `remoteTimeoutSeconds` | integer | Optional, 600–3600, default 1800. Generous last-resort router-side `timeout -s KILL`; the script bounds itself first. The local timeout is this value + 60 s |
| `roles.management` | object | `{"ip", "mac"}`. The SSH client device. Its MAC is protected |
| `roles.jd_adult` | object | `{"ip", "mac"}`. The adult device that must stay connected. Its MAC is protected |
| `roles.penn_child` | object | `{"ip", "mac"}`. The child device. It must be present, but it is **not** enrolled |
| `protectedHistoricalMacs` | array | 1–32 MACs to protect (for example Bryn's) that need not be present. None may equal a live role MAC |

MACs must be canonical lowercase `aa:bb:cc:dd:ee:ff`, unicast and non-zero. Live role MACs and IPs must be distinct from each other and role IPs from `host`, with one exception: `management` and `jd_adult` may have exactly the same IP **and** MAC (for example, both `192.0.2.10` / `02:00:00:00:00:10`). Matching only one field is refused. Child roles must remain distinct, and historical MACs must remain unique and separate from every live role. Repeated adult `--protect` arguments are deduplicated by the installer. Evidence explicitly labels the adult and management probes as sharing one confirmed device; this does not establish connectivity for a second adult device.

## Release identity and the shipped tree

The payload ships only the emitted tree: the entries of `router/release.sha256` plus `release.sha256` itself (the bytes `tools/freeze-router-release.py --emit` writes; wrappers stripped of `CF_TEST_MODE` blocks, modes 644/755/600). `router/cron` and `router/firewall.include` are tracked but not in the manifest and not used by `install.sh`, so they are never shipped. Any other tracked `router/` file outside the manifest, and any manifest entry whose file is missing, duplicated or malformed, refuses the plan (two-way check). The manifest must also list exactly the router's fixed set of 15 files (`install.sh`, `uninstall.sh`, `cfctl`, `cfctl-ssh`, `cfctl-scope`, `lib/platform-bootstrap.sh` and the nine `lib/` modules), the set `platform-bootstrap.sh` accepts; any other entry set refuses. The stripped `cfctl-ssh` and `cfctl-scope` must pass `sh -n`, as in the freezer.

Before anything is built the tool recomputes `CF_RELEASE_ID` from the shipped bytes with the freezer's formula and refuses on any mismatch: the nine module hashes, `cfctl` with its pin line blanked, and the stripped `cfctl-ssh` and `cfctl-scope`. It also requires `CF_RELEASE_MODULES` to equal the shipped module hashes, and `CF_BOOTSTRAP_PIN` in `install.sh`, `uninstall.sh` and `cfctl` to equal the hash of the shipped `platform-bootstrap.sh`.

`plan` discloses `emittedTreeSha256` (sha256 over the sorted lines `mode path sha256` of the emitted tree), and it is part of the plan digest, so the approval binds the emitted bytes and not only a commit. A test compares the tree and the id with `freeze-router-release.py --emit` output. The VERIFY phase then checks, on the router, each file listed in the manifest in the release directory named by the id and, for `cfctl*` and `lib/*`, in the place the installer puts it under `usr/sbin` and `usr/lib/couvrefeu`. Each must be a regular file and not a symlink (a FIFO or other special file is refused without being read), and its sha256 must equal the shipped digest; the installed `CF_RELEASE_ID` is checked too. Only those listed files are claimed to hash-match: modes, owners, extra files and the symlink status of parent directories are not compared.

If a listed file in the release directory or under `usr/lib/couvrefeu` (the inputs of the installed `uninstall.sh`) fails that check, the script does **not** run the installed `uninstall.sh` as root. It stops at VERIFY with `PHASE VERIFY FAIL installed_uninstall_inputs_mismatch <paths>; uninstall not attempted; journal retained` and `FAIL_AFTER_MUTATION VERIFY`, leaving Couvre-feu installed with its journal (`/etc/couvrefeu/backup`). Recovery is then a manual password login, which this tool never disables; resolve the cause by hand, and do not delete the journal. A mismatch only under `usr/sbin` is reported as `PHASE VERIFY FAIL installed_tree_mismatch` and the run continues to the normal uninstall, which fails the final result.

## Penn pilot, one or two devices (`penn-pilot.py`)

For the schema v2 operator sequence and live-use blockers, read the [v2 pilot runbook](../../docs/runbooks/live-penn-pilot-v2.md).

`penn-pilot.py` performs gate 3 of the [ordered live gates](../../docs/integration-004.md#ordered-live-gates) in one SSH session. It uses the same configuration schema. Use a separate config copy whose `authorizationPath` records approval of this exact pilot. Each run creates a `<UTC>-penn-pilot/` evidence directory. Here, `penn_child` **is** enrolled, and its MAC (with `penn_child_2`, both MACs) is the only MAC the policy may contain. The tool asserts this locally and again on the router before any write. With two devices the router does not trust the device-set parameters: in PAYLOAD it recomputes the `LC_ALL=C`-sorted pair from the two MACs that IDENTITY checks and refuses (`device_set_mismatch`) unless the `--rpc-allow` list and the expected `observed.kids` equal it. `remoteTimeoutSeconds` must cover the disclosed worst case (`minimumRemoteTimeoutSeconds` in the plan); with the default timing that is 3,651 s, so raise it from the 1,800 s default. The minimum is the pre-mutation budget (360 s) + one safe-band wait and the install allowance (72 + 240 s) + the per-phase worst cases (ENROLL 677, PAUSE 482, RESUME 362, EXPIRY 898, DNS 80 s; each `cfctl` call is a 72 s safe-band wait + the 45 s allowance + the 15 s KILL grace + 2 s polling slack, each counters snapshot 80 s, each probe iteration 40 s, each status settle 195 s) + the 480 s teardown reserve. A status settle is the first attempt's neighbor read (8 s) + the `timing.statusSettleSeconds` window (45 s) + one attempt admitted at least 1 s before the window closes (one 134 s `cfctl` call + 8 s neighbor read; the spare second absorbs 1 s clock granularity and the neighbor-hash forks); ENROLL and EXPIRY each carry one. Two devices add one `cfctl rpc-activity` call to ENROLL (811 s), so the minimum becomes **3,785 s**; the SCOPE phase adds one `cfctl` call plus two firewall-state reads (3 × 8 s each), 182 s, giving **3,833 s** for one device with SCOPE and **3,967 s** for two devices with SCOPE. Every shape exceeds a 3,300 s config, so raise `remoteTimeoutSeconds` to at least the plan's minimum (a schemaVersion 1 config is capped at 4,200 s here, above `first-rehearsal.py`'s 3,600 s, because the KILL grace and the longer teardown reserve put two devices over 3,600 s); the plan refuses below it. On the router, each phase starts only if elapsed time plus its worst case still leaves the teardown reserve, and every observe/expiry iteration and counters snapshot re-checks this; otherwise the pilot stops into teardown (`remote_budget_reserved_for_teardown`). Every timed pause is extended by the slowest `cfctl` call measured so far in the session (capped at the 45 s `cfctl` allowance, which the EXPIRY worst case adds on top of the pause length; the plan's `timing.cfctlAllowanceSeconds` discloses it), so a pause cannot lapse inside its own `cfctl pause` on a loaded host; the call still runs exactly once. Read-only `iptables`/`ipset` reads run under `timeout -s KILL 8`. Every `cfctl`, wrapper and uninstall child is started by `cfp_run`, which sends TERM at the allowance (45 s for `cfctl` and wrapper calls, `CFP_UNINSTALL_ALLOWANCE` = 240 s for the uninstall; exit 143) and KILL only `CFP_KILL_GRACE` = 15 s later (exit 137), so a hung child stops the run into teardown instead of stalling it. TERM first matters: with the os-trust profile every `cfctl` run takes `/tmp/couvrefeu-platform.lock` (`platform_lock_acquire`, `router/lib/platform-bootstrap.sh`), and `cfctl` and the installers trap TERM and release the runtime and platform locks (`router/lib/core.sh` trap handlers, `install-common.sh`); SIGKILL skips those traps and nothing clears the lock but a manual `cfctl recover-platform-lock`, which would leave the per-minute `cfctl expire` failing (`transaction_contention`) so pauses have no kernel time bound, and make the uninstall refuse. A busybox `timeout` signals only its direct child and has no `-k`, so `cfp_run` supervises the isolated child in the pilot shell itself, using builtin reads of real `/proc/uptime` and one-second polls. Each deadline carries up to one second of polling slack; KILL is scheduled a full 15 s after the TERM poll. A session-group signal can kill a polling sleep but cannot remove supervision. If the supervision clock becomes unreadable, the pilot commits to STOP: it temporarily ignores session HUP/INT/TERM so a full grace sleep inherits immunity, sends TERM to the isolated child, waits the remaining grace without repeating TERM, then KILLs and checks locks. That emergency path restores the mutation signal trap (or teardown ignore) and never reports success. The child is started with `exec setsid` and so leads its own process group: TERM at the allowance and KILL after the grace go to the whole group, and a group member that outlives a TERMed `cfctl` is KILLed when the call returns. This ends a foreground grandchild (`iptables -w`, `ipset`, `uci`) together with `cfctl`: a shell defers its TERM trap while a foreground command is running, so signalling `cfctl` alone would leave the trap waiting for the KILL and the grandchild running and mutating after the teardown starts. Evidence (busybox 1.33.1 `setsid` and util-linux `setsid`): in a non-interactive shell the background subshell is not a group leader, so `setsid` execs in place without forking; the child keeps the pid that `$!` reports and that `cfctl` records in the platform lock (`$$`), and that pid is the group id (pinned by test under `sh` and `busybox ash`). A `setsid` that did fork would return 0 in the parent at once while the child ran on detached (`cfp_run` would lose the child process group and `cfctl` would run unbounded), so the baseline runs `( exec setsid $CFR_SH -c 'exit 7' ) &` before any mutation and refuses with `setsid_forks` unless the status is 7. The group signal is `kill -TERM -PID` without `--`: busybox 1.33 `kill` rejects `--` yet still signals, which made the bare-pid fallback always run and send a second TERM that cut the child's EXIT trap (the lock release). `setsid` is a baseline prerequisite (`missing_tool setsid` refuses before any mutation), and TERM is reset in the child, which the teardown otherwise passes on as ignored. A TERM or INT that reaches the pilot shell while a child is in flight no longer starts the teardown on top of it: the trap only records it, `cfp_run` reaps the child (it ends by itself or at the supervised deadline), runs the stale-lock check, and only then stops with `SIGNAL interrupted` (or `platform_lock_stale_after_kill`). If the lock directory's `pid` file holds exactly the pid of a child that was signalled and ended non-zero (cron `cfctl expire` holding the lock legitimately never matches), the stop reason becomes `platform_lock_stale_after_kill` and the output carries `stale_platform_lock ...; manual recovery: cfctl recover-platform-lock; password login is the recovery path`; a lock directory without a `pid` file after such a child is reported as `platform_lock_unowned` (`INFO platform_lock_unowned ...` with the same manual recovery); the single uninstall still runs once and, refused by the lock, ends `FAIL_AFTER_MUTATION UNINSTALL` with Penn possibly still paused. The uninstall is TERMed at an allowance no shorter than the 240 s install allowance (never an arbitrary shorter deadline in the middle of a restoration), and a hung one is reported as `PHASE UNINSTALL FAIL uninstall_timeout` then `FAIL_AFTER_MUTATION UNINSTALL`. The teardown arithmetic stays inside the 480 s reserve: leg-2 cancel wait 75 s (the 60 s leg timeout plus 15 s) + one safe-band wait 71 s + uninstall 240 s + KILL grace 15 s + polling slack 2 s = 403 s, then the local reads, each `timeout -s KILL` bounded and failing closed (a killed read fails the snapshot instead of looking like an empty list): restore snapshot 5 x 8 s and connectivity 8 s on success = 451 s, snapshot and `cfp_kernel_state` 3 x 8 s on failure = 467 s. `CFP_KILL_GRACE`, `CFP_UNINSTALL_ALLOWANCE` and `CFP_LEG2_CANCEL_WAIT` are parameters from `penn-pilot.py` (single source of truth), not shell defaults. The installer (`install.sh`) is not KILL-wrapped: killing it mid-way is riskier than waiting for the router-side last-resort timeout.

```sh
python3 -I tools/live/penn-pilot.py plan CONFIG      # disclose, then:
python3 -I tools/live/penn-pilot.py execute CONFIG --expect-plan-sha256 HEX
```

### Config schema v2 (`scope_target`) and `config.pilot.example.json`

`penn-pilot.py` reads `schemaVersion` 1 (the legacy shape above, unchanged) or 2. [`config.pilot.example.json`](config.pilot.example.json) is the v2 example (fictional MACs and documentation IPs only). It is separate from `config.example.json` on purpose: `first-rehearsal.py` accepts only `schemaVersion` 1 and rejects the pilot-only roles, so the rehearsal can never be started from a pilot config by mistake (a test asserts this).

| | `schemaVersion` 1 | `schemaVersion` 2 |
|---|---|---|
| Extra roles | optional `roles.penn_child_2` | required `roles.scope_target` and `roles.ct107`; `penn_child_2` is refused |
| Install floor | `penn_child` (and `penn_child_2`) | `penn_child` (the Chromebook) only |
| Phases | the list below | `ENROLL`, `SCOPE-ADD-1`, `SCOPE-ADD-2`, `PAUSE`, `RESUME`, `MOVE`, `BULK`, `EXPIRY`, `DNS`, `INVENTORY`, `SCOPE-REMOVE` (see the v2 phase table below); the optional `SCOPE` negative test sits before `SCOPE-ADD-1` |
| `remoteTimeoutSeconds` | 600-4200 (at least the plan minimum) | at least `minimumRemoteTimeoutSeconds` (10,371 s for the shipped timing, 10,553 s with the `SCOPE` test) and at most `min(10800, minimumRemoteTimeoutSeconds + 900)` |
| Remote self-abort | none | the remote script begins its teardown at 70% of `remoteTimeoutSeconds` |

- `roles.scope_target` `{ip, mac}` is the phone of the same person. The later phases add it to Penn's scope and remove it again. It must differ from every role, the host, every protected MAC (including `ct107`) and the synthetic scope test MAC. The plan echoes it in an owner-confirmation line: confirm Penn owns that device.
- `roles.ct107` `{ip, mac}` is the CT107 infrastructure container. Its MAC must also be listed in `protectedHistoricalMacs`, so the protected set always holds the management device, the adult device, CT107 and every historical adult device. No pilot policy may name any of them.
- The policy validator builds each stage's expected policy from the config alone (enroll, enroll_phone, move, move_back) and refuses any other membership, any non-empty or non-list `pauses`/`schedules`, any `doh` other than empty lists, and any non-string id.
- The v2 plan digest binds the roles, the protected set, the platform profile, the source commit, the legs, the stage policies, the failed-block-all wording, the self-abort percentage, the operation ids and `configSchemaVersion`; a v2 plan missing any of them is refused. The stage policy revisions are 1 (enroll), 2 (phone), 5 (move), 8 (move back): `rpc-sync` needs `policy.revision == expected_revision + 1` and each `cfctl pause`/`resume` adds one (3-4 PAUSE/RESUME, 6-7 the `pilot_b` pause/resume). The three syncs the template derives from a stage are disclosed too, in `derivedSyncs` (digest-bound, with their operation ids): BULK pause_all (revision 9, both persons paused until router time + pause length + the cfctl latency margin), resume_all (10) and the final un-enrol (12, after the EXPIRY pause at 11). The router compares each planned revision with its own count before sending.
- The timeout cap exists so an unattended session cannot be given an arbitrarily long budget: a router-side `timeout -s KILL` that fires late leaves the pilot's changes in place longer. The break-glass cleanup path: recovery is a manual password login on the router. This pilot never disables or confines password/admin login to the router or CT107; follow "If the single uninstall is absent or refuses" below.
- Elapsed budgets and the self-abort use the router's uptime clock (`/proc/uptime`, `cfp_elapsed`), not `date +%s`, so a clock step cannot move them; wall-clock seconds remain only for the pause `--until` (the router compares it with its own time) and per-call latencies. v2 also refuses to start a phase whose worst case would cross the self-abort mark (`remote_self_abort_worst_case`).
- Leg cancel: if a stop happens after a `CFP_LEG2_READY <leg> <base>` marker and before that leg's confirming `rpc-status` read, teardown prints `CFP_LEG2_CANCEL <leg>`, then `CFP_LEG2_ACK_FILE <path>` (the path is `<stage>/leg2-idle`), then waits at most `CFP_LEG2_CANCEL_WAIT` (75 s, shared: the 60 s `CFP_SCOPE_LEG_SECONDS` leg timeout plus 15 s, so a leg still running when the stop comes can finish and be acknowledged) until ALL of: the file at that path exists (the driver's acknowledgement), the runtime and platform locks are absent, and the live scope file's sha256 is identical on two reads one second apart. Only then does it run the single uninstall. A quiet scope alone proves nothing (a leg that has not started yet is quiet too), hence the acknowledgement. On timeout it logs `leg2_quiesce_timeout <leg> no_acknowledgement|acknowledged` and still runs the uninstall (never fatal, the uninstall is the safety path). The router cannot stop a driver from starting a leg after the cancel marker; the T4 driver must not, and must create the acknowledgement file only once no leg is in flight, none will start and no `cfctl`/`cfctl-scope` process is alive on the router (see the T4 contract).
- An empty baseline scope list cannot occur after the scoped install, so `cfp_status_parse` treats it as a parse failure: `router/lib/core.sh` `cf_scope_file` requires 1-256 MACs, `install.sh` refuses an empty `--rpc-allow`, scope-remove refuses a floor MAC (`scope_mac_in_floor`), and `cf_scope_load` refuses an unscoped install (`scope_unscoped_install`); the pilot's floor (the Chromebook) is always in the scope.
- BULK checks the router's receipts by id: after `pause_all` and after `resume_all` it reads `cfctl rpc-status --json <operation id>` and requires the count of that id in the reply to be exactly 1 (`bulk_receipt_count_unexpected`). `rpc-status --json <id>` is a lookup by id, so the count is 0 or 1 by construction: the check verifies only that the router recorded a receipt under exactly this operation id (an absent receipt, or a reply of an unexpected shape, stops). It does not detect a replay or duplicate; that is the receipt's `baseRevision`/`acceptedRevision` check at the sync itself (`receipt_revision_unexpected`).
- `penn-pilot.sh` implements every v2 phase, and `execute` runs a v2 plan through the leg-2 pty driver `penn_pilot_leg2.py` (`LEG2_DRIVER_IMPLEMENTED` in `penn-pilot.py`). The four scope commit legs need a TTY and a typed confirmation, so the driver starts each one as a SECOND `ssh -tt` from the local tool under a Python pty. `plan` discloses every leg's full command line; each leg's whole ssh argv (the leg-1 argv with `-e none -tt` for `-T`, so the ssh escape character is off on the pty; the pinned known-hosts file and `StrictHostKeyChecking=yes` unchanged; the fixed command template last) is bound in the plan digest, and the driver re-checks the digest and the argv shape before it sends anything. See the driver paragraph below.
- Remote self-abort (v2 only): the remote script begins its teardown when elapsed time reaches 70% of `CFP_REMOTE_TIMEOUT` (stop reason `remote_self_abort`, checked at every phase start and inside every observe, expiry, settle and leg-poll loop), so the router-side `timeout -s KILL` (the full `remoteTimeoutSeconds`) is only a last resort. The mark is deliberately below the disclosed worst case: summing every worst-case wait (9,891 s before the teardown reserve for the shipped timing) can exceed 70% of any permitted timeout, and such a run ends STOPPED (restored), never PASS. Nominal runs finish far earlier (the worst case counts a 71 s safe-band wait on every `cfctl` call). v1 keeps its legacy shape: its worst case divided by 0.7 would exceed the 3,600 s cap, so no self-abort is applied there.

### v2 phases (`scope_target`)

The leg-2 handshake. Leg 1 is the single `ssh ... /bin/sh -s` session. At each scope commit step it waits for the safe band, prints one marker line `CFP_LEG2_READY <leg> <64 hex base>` (leg `2a` cfctl scope-add, `2b` cfctl scope-remove, `2c` cfctl-scope add, `2d` cfctl-scope remove; base is the scopeSha the leg commits against), then polls the live scope file (lock-free, so it never holds the lock the leg needs) until its sha256 equals the expected next scopeSha. It then confirms with ONE `cfctl rpc-status --json` read (scopeSha, the phone's membership, and that the listed scope hashes to the scopeSha). The leg's own report is never used. A scope that is neither the base nor the expected one stops (`scope_sha_unexpected`), a re-read that disagrees stops (`scope_reread_mismatch`), and `CFP_SCOPE_LEG_SECONDS` (60) without a change stops (`scope_leg_timeout`); teardown follows each stop.

| Phase | What happens (leg 1) |
|---|---|
| IDENTITY | As above, plus the phone (`scope_target`) is refreshed and must be fresh, unique and without a protected MAC on its IP (`scope_target_*` reasons). PAYLOAD derives every stage policy from the MACs and refuses (`policy_stage_mismatch`) unless the four policy parameters equal it |
| SCOPE-ADD-1 | `cfctl scope-preview` (read only; only the final JSON line is parsed, the hostname and protected MACs in its text are never logged); `scope_tty_required` refusal with stdin /dev/null (exit 1, exactly that reply, scope unchanged); marker `2a`, then `2b` |
| SCOPE-ADD-2 | The same preview through the `cfctl-scope` wrapper; four wrapper argv negatives (`scope-add bad`, short base, extra argument, missing MAC) must exit 2 with no output and leave the scope unchanged; marker `2c`; `rpc-sync` enrols the phone in `penn` (one receipt) |
| PAUSE, RESUME, EXPIRY | As above, now over both Penn devices |
| MOVE | `rpc-sync` moves the Chromebook to `pilot_b` (penn keeps the phone: a person with zero MACs is never created). `cfctl pause pilot_b` (timed): the Chromebook is in the kernel paused set and the phone is not, adult probes unaffected; resume; `rpc-sync` moves it back. The reply must show `pilot_b` gone and the filter/ipset fingerprint (slot letter normalised) must equal the pre-move one (`firewall_not_restored_after_move_back`) |
| BULK | ONE `rpc-sync` pauses `penn` and `pilot_b` (timed, same `until`), ONE resumes both. Each must be a single receipt, accepted at the next revision (`bulk_receipt_count_unexpected`). IPv4 and IPv6 paused-rule counts are recorded; a missing IPv4 rule or a set that does not hold both devices is `block_all_unchanged` (the decided wording constant), an IPv6 shortfall is recorded as `unmeasured partial_or_unconfirmed` and never retried |
| INVENTORY | `rpc-inventory --json` three times (centisecond timing) and once through `cfctl-ssh --rpc-only`. Version 1, one line, below 131072 bytes, no protected MAC listed, both Penn devices listed, and the same top-level shape in every sample and in the wrapper reply. The device count is recorded per sample and may differ (a lease expires, a guest joins). Evidence is the per-sample counts, the `truncated` flag, byte size, three timings, a hash of the top-level key set and a per-run-salted sha256 of the reply (salt from `/dev/urandom`, discarded). The reply, which holds hostnames and every other MAC, is never printed and is removed from the stage directory as soon as it is summarised |
| SCOPE-REMOVE | `rpc-sync` un-enrols the phone FIRST (`scope_mac_in_use` otherwise), then marker `2d`; the scope must return to the SCOPE-ADD-1 scopeSha. A `logread` count of the audit lines is recorded (`unmeasured` when absent or zero) |
| UNINSTALL, RESTORE, CONNECTIVITY | As above, plus a read-only `teardown_proof` (v1 and v2): no `runtime/.scope.*` candidate left, the `cf*` ipset/iptables/ip6tables line counts as before, the `/etc/crontabs` crond count back to baseline, no person in state, no release directory. A violation is `PHASE RESTORE FAIL teardown_*` |

New stop reasons: `scope_leg_timeout`, `scope_sha_unexpected`, `scope_reread_mismatch`, `scope_membership_unexpected`, `scope_tty_refusal_unexpected`, `scope_changed_by_refusal`, `scope_changed_by_negatives`, `wrapper_negative_accepted`, `scope_add_refused <code>`, `scope_target_in_scope_at_start`, `scope_target_no_evidence`, `revision_unexpected`, `policy_revision_mismatch`, `receipt_revision_unexpected`, `pilot_b_not_populated`, `pilot_b_left_populated`, `penn_not_phone_only`, `penn_not_restored`, `chromebook_kernel_state_not_*`, `phone_kernel_state_not_*`, `firewall_not_restored_after_move_back`, `block_all_unchanged`, `bulk_receipt_count_unexpected`, `inventory_*`, `wrapper_inventory_*`, `unenrol_not_observed` and `remote_self_abort`.

Privacy: the evidence directory is committed to nobody, but it is still kept free of household data. Fixture limits. The fixture cannot reach the shipped (stripped) wrappers' absolute `/usr/sbin/cfctl`, so the fixture-only `CFP_WRAPPER_DIR` (honoured only when the script runs under `CF_TEST_MODE`) points the wrapper positives at the repository's test-mode-capable wrappers; the stripped wrappers' positive paths are first measured live. The fixture's fake ssh runs the commit legs under a pty; that stand-in is test code, not the T4 driver.

The leg-2 driver (`penn_pilot_leg2.py`, T4). The local tool tails leg 1's stdout file and matches whole lines against `CFP_LEG2_READY (2[a-d]) ([0-9a-f]{64})` only. It starts the next planned leg (in the order 2a, 2b, 2c, 2d) once per marker, never two at a time, with the plan's digest-bound argv and the base from the marker (any other, repeated or out-of-order marker is ignored and counted in `ignoredMarkers`). The leg runs under `os.openpty`; the confirmation (last six hex digits of the scope target's MAC) is typed once, and only when everything the leg has printed so far equals exactly `<op> <mac> --base <base>` + newline + `Type the last 6 hex digits of the address (no colons) to confirm: `; anything else kills the leg (`prompt_mismatch`) with nothing typed. Each leg gets `timeoutSeconds` (60) and is killed with its process group at the deadline (`timeout`) and also when its ssh exits normally, so nothing it left behind outlives it; there is no retry of any outcome. One poll takes at most 64 KiB from a leg's pty and at most 64 KiB from its stderr pipe, so a leg that floods output cannot starve the deadline, STOP or cancel checks. A leg is killed when leg 1 prints a `STOP ` line (`killed_on_stop`) or `CFP_LEG2_CANCEL <leg>` (`killed_on_cancel`), when leg 1 ends or the local timeout fires (`killed_leg1_ended`), and no leg starts after either line (also not for a marker in the same read). The leg's pty descriptor is closed and the process reaped on every path. Evidence (`legs.json`, and `legs` in a v2 `summary.json`; a v1 summary has no `legs` key) holds only per leg: id, form, op, outcome, exit code, `ok`, the reply's reason codes, whether the confirmation was sent, byte count, local-stderr byte count and whole seconds. No line the leg printed, no MAC, no IP and never the confirmation is kept. Leg acknowledgement: the driver is local and the stage directory is on the router, so after a `CFP_LEG2_CANCEL` (a bare `STOP` does not enable it) it ends the running leg, starts none, and only then (once per run, the FIRST such line only; later paths are ignored and counted) reads the `CFP_LEG2_ACK_FILE <path>` line, which must match exactly `/tmp/couvre-feu-first.<6 alphanumerics>/leg2-idle` (anything else, or a line with no prior cancel, is ignored and counted in `ignoredMarkers`). It runs ONE extra ssh built from the leg-1 argv (same pinned options, `-T`), limited to 25 s (scan window plus connect and slack), output discarded, whose command is a short `/bin/sh` script. The script scans `/proc/[0-9]*/cmdline` (portable: `pgrep` is only used behind `command -v` elsewhere in this tool) for a process with an exact NUL-separated field `/usr/sbin/cfctl` or `/usr/sbin/cfctl-scope` (a leg, its `timeout` wrapper, or a cron `cfctl expire`; an exact field never matches the script's own command line), rescans once a second for a constant 15 s (`ACK_SCAN_SECONDS`; cron `cfctl expire` or the wrapper's timeout watcher briefly shows `/usr/sbin/cfctl`; 15 s plus the ssh connect fits inside the shared 75 s `CFP_LEG2_CANCEL_WAIT` (`LEG2_CANCEL_WAIT_SECONDS` in `penn-pilot.py`), and a test ties the two), and fails closed: if one is still alive after that it exits 3 and writes nothing (`busy`, final, the ack ssh is not retried). Otherwise it refuses an existing path or symlink and creates the file with `set -C`. The result (`sent`, `busy`, `failed`, `refused` or `none`) is the `ack` key of `legs.json`; none of the non-`sent` results is fatal (leg 1 then logs `leg2_quiesce_timeout` after its 75 s wait and still uninstalls). `refused` means the pinned files below changed. Leg 1 still never trusts a leg: it re-reads the router state itself. The driver reuses the pinned leg-1 ssh options only and refuses any leg argv that weakens host-key checking, so password and admin login to the router and CT107 are untouched. Remote bound: each leg command uses a fixed `/bin/sh` supervisor with positional arguments and a digest-bound script. It starts the commit with `setsid`, preserving the pty on stdin, sends TERM to the commit's entire process group at `timeoutSeconds`, then KILL after 15 s if needed, waits for the child and clears remaining group members. This also ends a foreground child (for example `sync`) that would otherwise defer ash's TERM cleanup. The supervisor ignores HUP, INT and TERM so a dropped SSH channel cannot end its watchdog; the commit resets those signals. The baseline's non-forking `setsid` check is required. The driver refuses any change to the fixed script, operation, timeout or grace. Only the backstop KILL skips cfctl's lock traps, and the stale-lock report applies then. The ack scan recognises a live leg through the supervisor's positional `/usr/sbin/cfctl` or `/usr/sbin/cfctl-scope` field. For the wrapper form `env` and `cfctl-scope` hand over by `exec` (same pid), so TERM reaches the commit and its descendants. Local BusyBox ash fixtures verify tty confirmation, foreground-child TERM/EXIT lock cleanup and watchdog survival after HUP; real Dropbear/OpenSSH behavior is first exercised live. Pinned files: before leg 1, before every leg and before the ack the driver re-hashes the known-hosts file and the identity (`-i`) file with the plan's lstat-checked `regular_file_sha256` and compares them with the digest-bound `knownHostsSha256` and `adminPublicKeySha256`; a change, a missing file or a symlink starts no further leg and sends no ack (`pinned: changed` in `legs.json`; leg 1 then stops at its leg timeout and tears down as for any leg that never ran). Before leg 1 it is a refusal with nothing sent. A swap between the hash and ssh reading the file is not closed by this: it needs local write access to the operator's own pinned files (accepted residual). Signals: during `run`, SIGTERM, SIGHUP and SIGINT raise `KeyboardInterrupt` (main thread only), the cleanup kills and reaps the leg and leg 1 with signals blocked in the main thread AND in every helper thread (the payload feeder and the host-probe thread block them as their first action: a process-wide signal goes to any thread that does not, and CPython then runs the handler in the main thread), and only the first signal acts: a later one is ignored, so nothing interrupts the cleanup half way. The mask is captured and the signals blocked before the handlers go in, and a stop that arrives while a child (including the acknowledgement SSH) is being started is held until that child is assigned (so its entire process group is killed and it is reaped); the residual window is the fork and exec themselves, and SIGKILL cannot be stopped; the pilot then records UNKNOWN as for Ctrl-C. The plan's legs are deep-copied at construction. `tests/fake-leg-ssh.py` plays `ssh -tt` in the fixtures; a real router, Dropbear and OpenSSH's own pty handling are first exercised live. The local ssh client's own stderr (banners, warnings, `Connection to ... closed.`) goes to a pipe that is only counted (`stderrBytes`), never matched or kept; text the REMOTE prints before the prompt (a pre-auth banner relayed over the pty) makes the leg refuse (fail closed). A marker that arrives while the previous leg's ssh is still closing is held (one slot) and starts when that leg ends; a STOP, a cancel or the end of leg 1 drops it.

The remote script is the filled `first-rehearsal.sh` with its final call removed, followed by `penn-pilot.sh`, which reuses every `cfr_*` helper. It runs these phases in order:

With two devices the second device passes the same checks (`penn_child_2_*` reasons), and neither Penn MAC may appear on the other's IP. PREREQ validates the exact `--rpc-allow` arguments |
| BASELINE | Router-side DNS (`nslookup example.com <router LAN IP>`, centisecond timing), management/JD ping and crond count (split: `etc` = crond whose crontab dir resolves to `/etc/crontabs`, `other` = any other crond such as GL firmware's `-c /tmp/gl_crontabs`; the `MEASURE crond_processes` line reports `baseline=etcN,otherM`). All read-only. Tolerance: baseline maximum + 1.5 s DNS, + 500 ms management RTT. A ping is a STOP signal only if it answered at baseline |
| INSTALL | Scoped activation `--rpc-allow <penn MAC> [--rpc-allow <second MAC>] --activate`. No `authorized_keys` or service-key provisioning (`service_key_confinement: unmeasured, not exercised`) |

With two devices, one read-only `cfctl rpc-activity --json` follows: `rpc_activity_devices` is `measured listed=k/2` when the router exposes devices, `unmeasured` otherwise; a listed MAC outside Penn's set stops the pilot |
| SCOPE (optional) | Only with `scopeNegativeTest: true`. The fingerprint compares exactly three things: the `firewall.owned` slot instance (letter, inode, nanosecond mtime), every `ipset save` `create`/`add` line of a `cf*` set, and every `iptables -t filter -S` and `ip6tables -t filter -S` line with a word starting `cf` (Couvre-feu chains and sets); the `nat` and `mangle` tables are not compared (MEASURE detail `filter_ipset_slot_unchanged`). Anything else stops the pilot into teardown (`scope_not_cleanly_rejected` or `firewall_changed`); if the safe band never opens the call is not made and the stop reason is `safe_band_unavailable`. **Status settle (ENROLL and after expiry).** `cfctl status` reports `drift:true` whenever the effective digest (usable canonical LAN address bindings plus the protected list) differs from the one recorded at the last confirm. A binding change after the confirm (a usable address appearing, disappearing or changing owner) can do this with `errors:[]` until cron `cfctl expire` re-confirms within a minute. IPv6 REACHABLE/PERMANENT/STALE/DELAY/PROBE now supply identical binding evidence, so state-only aging among them does not change the digest; FAILED/INCOMPLETE/NOARP/NONE supply none. IPv4 lease/freshness behavior remains unchanged. A prior live pilot stopped at ENROLL (`penn_not_observed`) on IPv6 reachability aging under the earlier fresh-neighbor classifier. These two gates therefore re-read status, read-only, every `pollSeconds` (with the budget check and adult probes) until the gate passes, giving up `statusSettleSeconds` (45 s, plan-disclosed and digest-bound) after the first read. Only a single-line reply with `drift:true`, `errors:[]`, `desiredRevision` and `confirmedRevision` both equal to the revision the pilot's own calls set (1 after ENROLL; +1 for each pause and the resume, so 4 after expiry, which cron `cfctl expire` does not change) and the gate's expected kids/pauses is waited out. Every clean reply must also have both revisions equal to the expected pilot revision, including the initial read and any read after drift. Non-empty errors, a null, stale or unexpected revision (including a never-confirmed apply that cron could later repair) or a kids/pauses mismatch stop immediately with the gate's reason. No `rpc-sync` or other mutating call is ever retried. Each attempt's status read is followed by `INFO status_settle_neigh <phase> attempt=N` (the read-only `ip neigh show dev br-lan` table, with IPv4 addresses kept, role MACs named, other MACs and every IPv6 address replaced by a 12-hex prefix of sha256 over a per-run salt plus the token; the salt comes from `/dev/urandom` once per run and is never logged or written, and without it the line says `salt_unavailable` and nothing is hashed) so the changed neighbor can be named within one run but not linked across runs, and the gate logs `INFO status_settle <phase> attempts=N waited_s=S` (`not_transient` or `gave_up` on a stop). A gate that passes only after re-reads also prints `MEASURE status_settle measured settled_after_drift phase=<phase> attempts=N waited_s=S`. The PAUSE, RESUME and expiry-pause gates are not settled: they check the reply line that the mutating call prints right after its own confirm, which is the evidence for that call, and a wait there would eat into the timed pause.

**IDENTITY refresh probe.** A device idle on Wi-Fi can hold a STALE neighbor entry. Before the freshness check, IDENTITY sends each Penn device two ICMP echoes from the router (`timeout -s KILL 5 ping -c 2 -W 1 -q`, the BusyBox flags `cfp_ping` already uses), with a neighbor-table read before and after the probes. If a device was initially outside REACHABLE/DELAY, its probe must succeed: transmitting alone can change STALE to DELAY without a reply. Initially fresh devices retain the existing freshness check even if ICMP is unavailable. This is a network probe, not a state change: nothing on the router is written. A device that is still not REACHABLE/DELAY is refused as before (`penn_child_not_fresh`, `penn_child_2_not_fresh`).

After `MUTATION_BEGIN`, every outcome ends in that one teardown. This includes an adult-probe STOP, a failed gate, an exhausted time budget and an installer failure, provided the installed recovery `uninstall.sh` exists. The teardown is part of the approved procedure, not a retry. If it ends with exact restoration, the last line is `PENN_PILOT_STOPPED_RESTORED`, or `PENN_PILOT_STOPPED_RESTORED_CONNECTIVITY_FAILED` (outcome `STOPPED_CONNECTIVITY_FAILED`) when the management or JD neighbor check failed afterwards; if the teardown itself fails, it is `FAIL_AFTER_MUTATION`. Only `PENN_PILOT_PASS` means that every phase passed and the snapshot matched exactly. Even then, packet blocking is claimed only when counters rose.

### Accepted installer residual; M4b blocks live use

The pilot's INSTALL step is deliberately unbounded: a hung installer can outlive the remote timeout, leaving an empty-policy installation and a stale `/tmp/couvrefeu-install.lock`; nothing has been enrolled or paused at that stage. Do not add a KILL watchdog: SIGKILL skips lock cleanup, and a kill before the journal is ready makes uninstall refuse (`router/lib/install-common.sh`, lock acquisition/cleanup and `preflight`). The single automatic uninstall cannot recover that state.

Manual recovery uses password login to the router, which is never disabled. Confirm that no installer or recovery process remains before removing a stale install lock, then run the installed uninstall as described in the [rehearsal recovery instructions](../../docs/runbooks/live-first-rehearsal.md#stale-install-lock-recovery). A missing/incomplete journal still requires manual recovery; removing the lock does not repair it.

Accepted on 2026-10-23 as a documented residual for M5 code merges. **M4b blocks the first live rehearsal and permanent install:** router dead-owner recovery for the install lock, uninstall tolerating a pre-journal kill, a new release id and a full adversarial review/test cycle are required first.

### If the single uninstall is absent or refuses

The last lines are then `PHASE UNINSTALL FAIL ...`, `PENN_KERNEL_STATE paused|clear|unknown` and `FAIL_AFTER_MUTATION UNINSTALL`, with `DIFF` lines showing what is left. Couvre-feu stays installed with its journal; do not retry and do not rerun install or uninstall to "clean up".

- `PENN_KERNEL_STATE paused` means Penn's MAC is still in the pause set and Penn is still blocked. The pause rules have no kernel time bound. Only `cfctl expire` (cron) or `cfctl resume penn` (a mutation that needs its own approval) lifts the pause. Both refuse while uninstall recovery markers exist under `/etc/couvrefeu/backup` (`uninstall_recovery_in_progress`), which happens when uninstall refused after kernel cleanup began. `unknown` means the set could not be read; treat it as paused.
- Do not run `cfctl remove-fw` by hand. Once recovery markers exist, it is refused without the installer's token, and only `uninstall.sh` runs it.
- Follow the [rehearsal runbook](../../docs/runbooks/live-first-rehearsal.md) failure guidance: wait for `/tmp/couvrefeu-install.lock` and `/tmp/couvrefeu-platform.lock` to clear, read `<stage>/phase.log` and `child.log` for the refusal reason (drift, lock contention, kernel cleanup), and resolve that cause explicitly. Then, as a separately approved step, run the installed `/etc/.couvrefeu-release-<id>/uninstall.sh` once. It takes no arguments, and it is the only supported way to remove the firewall slots, cron entry and files and to restore the originals. Never delete the journal (`/etc/couvrefeu/backup`).

Every `cfctl` call waits until the router clock is between seconds 15 and 45 of the minute and no runtime or platform lock is held. That way it never races the per-minute cron `cfctl expire`, which fails on lock contention instead of waiting.

The pause rules (`--match-set cf2_<slot>_p src -j REJECT` and `-o br-lan -d <ip> -j REJECT`) have **no** kernel `-m time --datestop` bound. Only cron `cfctl expire` ends a timed pause. For that reason the pilot uses only timed pauses.

On the host, a thread samples RTT and a direct DNS query to the router before, during and after the session. These samples are evidence only: they cannot stop the remote script, but a disruption beyond tolerance prevents PASS. `summary.json` labels each measurement `measured` or `unmeasured`.

Never commit real MACs or IPs. Protected devices are listed only in the private config (`protectedHistoricalMacs`).
